# Spec: Android release runbook, target tags and notes, PR CI and release CI

Consumes [intent/android-release.md](../intent/android-release.md). The maintained documents are the specification of the procedures; this file states what each must contain and how the tools behave.

## Release convention (AC1)

- `docs/operations/github-releases.md` names one tag form per delivery scope: `android/`, `ios/`, `webapp/`, `backend/tw-svc/`, `backend/tw-gather/`, `backend/server2/`, each followed by `vMAJOR.MINOR.PATCH`. The Cordova forms remain as historical rows.
- Store apps have candidates `-rc.N` (GitHub pre-release) for binaries on test tracks and a final tag at the same commit when the binary goes to production. Other scopes have none.
- Tags are annotated, at an exact commit, never reused. Releases are created from an existing tag, never as "Latest".
- `scripts/release-notes.mjs --scope <scope> --version <version> [--commit <ref>] [--from <ref>]` prints a draft: source commit (40 characters), scope, tag, previous release, the changes merged under the scope's paths on the first-parent history since the previous final tag contained in the commit, the scope's identity lines and the status fields. It reads Git only.
  - A merged pull request appears with its title and number; a squash commit with its own subject; any other commit with its subject and short hash. No change: one line saying so.
  - Status 2 with a message and no output for: an unknown scope (own names of the scope list only), a version that is not `MAJOR.MINOR.PATCH` or `-rc.N`, a candidate for a scope without candidates, an existing tag, an unresolvable commit, a version that is not above the newest final release the commit contains, a `--from` that is not an ancestor of the commit, no previous final tag and no `--from`.
- `scripts/release-notes.mjs --check <file> --tag <tag> [--commit <ref>]` checks the notes for the tag that is about to be published. It passes when no `<fill in>` remains, the source commit is a full SHA (equal to `--commit` when given), the notes' `Tag:` equals `--tag`, their scope is the tag's, a candidate tag belongs to a scope with candidates, and the tag exists at the source commit; otherwise status 1 naming each problem. `--tag` is read as a tag name of this convention, never as a revision expression; without it, with a tag of another form, or with an unreadable file the status is 2.
- Neither mode writes a tag, a Release or a file.

## Android release runbook (AC2)

`docs/operations/android-release.md` orders: version freeze; release CI on the full SHA; the manual emulator gates with their commands and prerequisites; the export of the candidate, its local build and signing with `check-apk.sh`; the physical-device gate; candidate tag and notes; store declarations and test tracks; production tag, staged rollout and halt criteria; close; halt and rollback. Each step states who acts and what completes it. Steps needing private inputs, the signing key or store access are the operator's.

`android/tools/release/export_candidate.py <full SHA> <new directory> --private <directory>` is the first command of the release build. It writes every file of `<SHA>:android` from the object database (blob bytes and mode; replaced objects and outside configuration disabled), refuses a tree with a symbolic link, a submodule or an unsafe path, reads the directory back (exactly the commit's paths, each with the blob's hash under `git hash-object --no-filters` and its mode), then writes `google-services.json` and `private.properties` from the private directory as new files with mode 0600 and `CANDIDATE`, in a directory of mode 0700. The directory's name must not exist, a link included and however the name is written (`name/`, `name/.`), a path with `..` is refused, and the directory must lie outside the checkout, decided before anything is written; a failure removes the directory the tool made; the checkout is never changed. Status 1 when refused or failed, 2 for usage or a name that is not a full SHA. `test_export_candidate.py` checks it in PR CI against checkouts in every such state (changed, staged, untracked, ignored with non-ASCII and quoted names, index flags, line-ending and export attributes, a replaced object, tracked links, tracked private inputs), comparing each exported file with `git cat-file blob`.

`android/tools/release/gradle-release.sh` runs `./gradlew --no-daemon --no-build-cache --gradle-user-home <home> assembleRelease` in an export (where `CANDIDATE` is and `.git` is not) with a new environment (`env -i`) that holds only the variables the script lists (locations and locale) and `GRADLE_USER_HOME`: no other variable of the shell, whatever its name, reaches Gradle. It refuses to start with a Gradle init script in the Gradle user home or a home that is not an absolute path, gives Gradle the home it inspected, names the variables it kept out (taken from the environment as names, so no line of a value is shown) and the path of the user's `gradle.properties` without reading it, and ends with Gradle's status. `test-gradle-release.sh` checks it in PR CI with a stand-in `gradlew`.

`android/tools/release/check-apk.sh <signed.apk> <installed-store-release.apk>` reports one line per check and fails (status 1) on: an invalid signature of either APK; a set of signer certificates or a package different from the store release's; an APK digest it cannot compute; a `versionCode` not above it; a `versionName`, `versionCode`, `minSdk` or `targetSdk` different from the checkout's `app/build.gradle.kts`; a debuggable APK; Google's sample AdMob app ID or none; no Firebase configuration. It prints the identity lines for the notes and changes nothing. Status 2: usage, a missing file or missing SDK tools.

## CI tiers (AC3, AC4)

- `docs/development/ci-tiers.md` defines PR CI and release CI, the rules for placing a check, the measured state of each target and the Android split.
- `.github/workflows/android-release.yml` runs on `workflow_dispatch` (input `ref`: the full SHA), nightly, and on pull requests that change the workflow or `android/tools/release-ci/`. Jobs: the commit to verify; the PR workflow's jobs on that commit (`android.yml` as a reusable workflow); `lintRelease`; device suites on hosted emulators (phone API 36, phone API 24, tablet API 36, foldable API 36); a final job that fails unless all passed and names the commit.
  - `ref` is required; a dispatch whose `ref` is not the full 40-character SHA of the checked-out commit fails.
  - The nightly run skips every job when the paths that start the Android PR workflow and the release workflow are unchanged since the last passed nightly run; an unknown last commit or a git error runs it.
  - No secret, no environment, `contents: read` (plus `actions: read` for the nightly comparison). The emulator action is pinned to a commit SHA.
- `instrument <file> <arguments>` (`android/tools/emulator/offline.sh`) runs `adb shell am instrument -w -r` and keeps adb's status; `instrumentation_passed <file> <count> <adb status>` passes only for an adb status of 0, exactly `<count>` passed tests, no failed, crashed, ignored or assumption-skipped test, and a finished instrumentation. The release CI suites' runners (`run-device-tests.sh`, `run-native-smoke.sh`, `run-shell-fit.sh`, `run-window-fit.sh`) decide by them. In PR CI, `test-instrumentation-passed.sh` checks the decision against recorded outputs and `release-ci/test-runners.sh` runs each suite through `run-suites.sh` with an adb test double: a passing output with a failed adb, and a skipped test, must fail.
- `android/tools/release-ci/run-device-tests.sh <out> [Class[:name=value] …]` installs the debug and test APKs anew per class on an offline emulator and requires as many passed tests as the class declares `@Test`.
- `android/tools/release-ci/run-suites.sh <out> <suite> …` runs the named suites in turn, continues after a failure, writes `summary.txt`, exits 1 when any failed and 2 for an unknown suite.
- `android.yml` keeps its pull-request and push behavior; its measured time stays within 2–10 minutes.

## Not specified here

Signing configuration in Gradle, Play upload automation, GitHub environments and secrets, the iOS and server2 CI splits, and fixes of product or test defects that release CI reveals beyond what its own run needs: the two lint annotations for `lintRelease`, and Robolectric's Android runtimes resolved through Gradle and read offline (`app/build.gradle.kts`), because the download Robolectric otherwise makes during the tests failed the reused PR job in two of three hosted runs.
