# Forecast coverage specification
Input: [intent](../intent/issue-2676.md). Scope: legacy server only.

A forecast coordinator per Manager/product snapshots requested publication strings and owns a bounded run. Same-publication callers join; another publication receives busy until completion/deadline. Coordinate and DB reads wait `GATHER_FORECAST_READ_TIMEOUT_MS` (default three seconds) with maxTimeMS one second shorter; coverage records report read duration and read failure. Read failure terminates without unchecked HTTP. Nine-minute forecast deadline cancels collector/retry admission; late callbacks are ignored and cannot clear a newer run. Already issued Mongo operations may settle; no new write is admitted after expiry, and controlled writes are publication-fenced so a settling older write cannot replace a newer publication (DB2 `pubDate <= own` update with absent-slot `$setOnInsert`; DB1 compare-and-set on the read `pubDate`, refusing downgrades). Because that fence cannot order two writes of the same publication, a run of a publication is refused while an expired run of the same publication still has admitted writes settling. Ultra-short publications are updated by KMA every ten minutes: per AK (2026-10-04) each process performs one full refresh walk per current ultra-short publication from `GATHER_SHORTEST_REFRESH_AFTER_MS` (default base+40min) within a one-hour window, consumed only by a successful full walk; `0` disables it.

Coverage uses exact top-level publication (DB1 string / DB2 UTC BSON) and coordinate. Short expected slots start the hour after base and run hourly through +2 days for early publications, +3 for 17/20/23, then the final day at 00/03/06/09/12/15/18/21. Ultra-short is the next six hourly slots. Short requires TMP/SKY/REH/PTY/POP/PCP/SNO and wind fields in each slot; TMN06/TMX15 only when that publication supplies them. Ultra-short requires T1H/SKY/REH/PTY/RN1/wind/LGT; POP is required for publications at/after 202606231100. WAV is conditional and not a completion requirement. Finite zero and signed temperature/wind/lightning remain valid; schema sentinels and provider +/-900 missing values are incomplete. Extension-day precipitation/wind codes remain existing numeric storage; no API conversion changes.

All parsed rows must match requested publication and coordinate. Rows outside the expected horizon are dropped before writes, except a valid row within one day after the final expected slot (production counts show one extra slot); each expected slot appears once. Validate the complete batch before writer admission so incomplete provider horizons/categories do not relabel older data. DB1 controlled writes replace required fields of overlapping requested slots rather than merging them from old publications, keep only conditionally absent same-day TMN/TMX and optional WAV, and preserve outside slots and retention limits. DB2 keeps per-slot documents with the publication fence above. Both writer paths stop new save/update admission after cancellation, retain the original publication, and propagate write errors. Coverage is read back after collection including error outcomes; errors never produce successful completion. Persisted complete grids are skipped after coordinator recreation without process coverage caches or schema markers, except the AC1 amendment: one scheduled ultra-short refresh walk per current publication per process. DB1 coverage cannot reconstruct per-field provenance for pre-existing legacy arrays, and DB2 cannot tell schema defaults (ultra-short `lgt=-1`) from received values; such legacy rows are trusted only for the publication current at deployment, and newly admitted forecast batches are validated before relabeling.

Keep #2604 concurrency, retry ceilings, rotation and rejection logic. Actual onPageRequest attempts accumulate in run control across passes/pages; sanitized coverage/result records contain product, publication, expected/complete/pending and attempts. No shared quota cooldown extension to these products.

No schema migration, deployment or backfill. Rollback reverts code; existing documents remain readable. Tests use synthetic full-grid adapters and real loopback HTTP/temporary Mongo4.4 with Node16/Mongoose5.1.2. Production readback remains separately gated. Reject document-exists and >=publication shortcuts: neither proves exact complete forecasts.

2026-10-04 rollback amendment (issue-2676-r2; [intent](../intent/issue-2676.md)). Ultra-short publication identity: a request at `HHmm` (KMA `HH30`) is answered with the provider's base hour `HH00`. The accepted persisted identities of a requested ultra-short publication are the same-date `HH00` echo and the literal request; any other date/hour is rejected. Request validation (`baseDate`/`baseTime`), batch admission (`pubDate`) and coverage queries (DB1 string / DB2 UTC BSON `$in`) use this one identity set. The parser and writers keep storing and fencing the echoed `pubDate`; horizon, POP threshold and the refresh window keep using the requested time. Short publications keep exact identity.

DB2 coverage reads run as one aggregation: `$match` on accepted `pubDate` and the expected `fcsDate` values (existing `fcsDate` index), then `$group` per coordinate adds each `fcsDate` whose slot expression holds: payload date/time equal to `fcsDate` in KST and every required field within the JS bounds (BSON comparison order limits `(-900, 900)` to numbers; issuance-specific TMN/TMX apply only at their slots). Only coordinates with every expected slot are returned. The JS rule and the Mongo expression come from one field-rule table; offline tests evaluate the generated stages with Mongo semantics and a real-Mongo differential smoke covers each required field and invalid value. `$match` field predicates were measured slower than `find` (2.2 s versus 0.74 s locally) and were rejected. Because the measured aggregation (about 1.05 s locally at production volume) has no headroom against the former 2 s `maxTimeMS` on production hardware, the `GATHER_FORECAST_READ_TIMEOUT_MS` default becomes 10 s (`maxTimeMS` 9 s). DB1 reads stay a `find` on the accepted publication strings. No index or schema change. Read failure still terminates the run without unchecked HTTP.

2026-10-04 late-publication amendment. Scheduler minute checks move from 13 to 12 (short) and from 48 to 47 (first ultra-short poll); other minutes and frequency stay. The collector marks a grid `notPublished` when its first page answers `resultCode 03` or a normal header without rows; the Manager raw-validation hook marks a response that consistently names an older publication. For forecast runs both stay pending without entering the immediate #2604 retry passes; current-observation handling is unchanged. After each walk the coordinator reads coverage; if grids remain pending, the read succeeded, keys are not exhausted and offsets remain, it waits until the next `GATHER_FORECAST_RETRY_AT_MS` offset from the run start (default 180000,480000) and walks the pending grids again. Only the first run of a publication per process has these re-walks; later runs walk pending grids once. `GATHER_FORECAST_DEADLINE_MS` default becomes 840000 so the final walk fits; offsets must be increasing and below it. Records: `forecast-pass` adds `notPublished`/`previousPublication`, `forecast-retry` per delayed walk, `forecast-collection` adds `walks`.
