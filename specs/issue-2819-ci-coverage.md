## Required behavior

**AC1 — Every event gets a minimum audit; relevant events get retained heavy checks.** Every PR and every push to master triggers the Server2 workflow; do not use workflow-level path filters. An always-run owned scope/layout check examines the **full root event diff, including both rename endpoints**, and the whole tracked layout/resource boundary. For `server2/**`, `server/**`, `.github/workflows/server2.yml` or other explicitly identified oracle inputs, execute both existing independent goldens and full foundation checks. `server/**` deliberately covers legacy handlers and maintained/public inputs rather than guessing a narrow stale list. Known unrelated-only changes still receive the layout audit and a receipt explicitly stating heavy foundation/goldens not run; they do not pay for an unnecessary Rust rebuild or receive invented heavy PASS. Unknown/ambiguous paths or classification fail closed. In particular, a root/tools asset or unexpected root Rust/build asset cannot escape because it is outside a positive workflow path filter. This is static scope/layout enforcement, not a claim that arbitrary source semantics can be classified automatically. Keep permissions contents:read, pinned actions, foundation45/goldens30 budgets and independent heavy job identities. No pull_request_target or privilege-setting change.

**AC2 — Placement keeps the correct range and meaning.** The owned CI selector records event, exact head/base, full root changed/rename inventory, selected scope, declaration identities and heavy-check run/not-run disposition before running checks. Never filter the PR's changed-file inventory to server2 only, silently move the base forward, auto-select one declaration from several, or drop rename endpoints.

- A server2/workflow PR uses the actual PR base SHA through its current checkout and exactly one changed reviewed task declaration (or an explicit reviewed local declaration where already supported). The full root PR range, all outside changes/renames and the entire tracked server2 layout/resource boundary are checked. Mixed legacy changes require exact outside exceptions.
- A **known unrelated-only** PR/push still runs the whole tracked layout/resource audit and emits `layout-only` with both heavy checks explicitly not run. Unrelated classification requires a positive, bounded rule over the full changed/rename inventory; unknown root/tools assets and ambiguous changes fail closed rather than being accepted through a default else branch. Existing root Rust/resource violations remain rejected. A rename from a relevant/unsafe path to an unrelated destination never drops the source from classification.
- A **pure-legacy** PR/push (no server2 or workflow changes) has no server2 implementation-task path approval. Foundation still executes existing tests/build/smokes, and placement explicitly performs its whole tracked layout/resource audit; the receipt must label it `layout-only`, not a fabricated task-diff PASS. Relevant root Rust/resource violations remain rejected. The full event range is retained in the receipt; source classification examines all changes before selecting this mode.
- A server2/workflow **master push** uses exact nonzero event `before..after`, even if multiple PR merges are included. It validates every changed task declaration and requires the union of their exact declared scopes to cover **every root-range changed/renamed path**, plus the whole tracked audit. This is labeled push-range coverage, not retrospective proof of independent PR approval. Missing declarations or uncovered paths fail; each declaration remains format/policy validated. Deleted/renamed declarations must have an explicit reviewed disposition, never silently disappear from the candidate set. Initial implementation may fail closed on such deletion/rename rather than invent permission from old versions.
- Zero/missing/unavailable before for master-push scope is an explicit incomplete-range failure, not a merge-base fallback. An ordinary unrelated branch event is not relabeled master. No new branch-protection semantics are claimed.

**AC3 — Golden contracts stay independent.** Reuse the current canonical offline recorder, pinned Node16.20.2/lock and exact two-fresh-recordings comparison. No fixture update, automatic re-record acceptance, expected value derived from Rust, or weakening of body/status/header/source checks. G1 historical provenance reconciliation is a separate **required** root-owned task. G2 can implement its independent wiring in parallel, but cannot declare G1 complete or add a premature global freshness policy. Legacy-only trigger may expose a genuine S02 drift; retain and report it rather than refreshing the baseline.

**AC4 — One exact source identity reaches build and artifact.** Resolve actual PR head or master after SHA as a full40 lowercase hash, verify the checkout's server2 tree matches it, then pass that same process-scoped `SERVER2_BUILD_REVISION` to **all Cargo child builds** and the existing verify/native-artifact exporters. Reject a conflicting caller stamp or source-tree mismatch before building. Runtime record stamping is compile-time and separate from manifest metadata; fresh CI must show the selected stamp on an actual record. The checked-out PR merge commit must not be mistaken for PR head. No Rust runtime change or new source-of-truth variable is needed.

**AC5 — Preserve verified inputs for a bounded consumer window.** Set the existing exact native-artifact upload to 30 days (root-approved bounded CI window, not production recovery authorization). Keep its name/path/if-no-files-found:error, verified-only ordering, native.tar.gz hidden files/modes and existing full source/11-role+2-probe exporter. Do not upload all reports or secrets. Root preserves required evidence and recovery inputs before expiry; 30 days does not guarantee indefinite retention or qualify a previous release.

**AC6 — Scoped verification and review.** Intended Python regression Red/Green, a separate local command-level CI-selector/placement functional smoke, unchanged oracle/source fingerprints, full declaration/artifact checks, eligible independent review and current PR CI are required before pre-merge readiness. No local full Rust release rebuild is required merely to repeat unchanged Rust evidence; normal fresh foundation CI remains required. Master event dispatch can be simulated locally, but its actual hosted execution occurs only after separately authorized integration and is not a pre-merge result. No test or CI execution has occurred in this preparation.
