# Acceptance for the restart bound work

- **NO-501:** a stored read the request waits for that fails because the store is slow, busy or unreachable never fails the answer. On the S06 loopback peer with the raw reads of a family held past the catalog's 3 s deadline after a producing process stored every family, a restarted process answers 200: with the forecast-zone list held, within 3 s (the zones taken at the head start, the read given up at the bound) with the zones of an empty store and the producing process's mid forecast and short rows (`a_zone_read_past_the_catalog_deadline_answers_with_the_empty_store_zones`); with the current observations' grid held, the producing process's whole answer, the latest publication asked once of its provider double (`a_grid_read_past_the_catalog_deadline_answers_from_the_provider`); with the town RSS and the three mid families held, the producing process's whole answer, each asked once (`rss_and_mid_reads_past_the_catalog_deadline_answer_from_the_providers`) (`tests/domestic/full_response.rs`). Only timeouts, transport and admission failures and error statuses leave a read absent; corrupt, invalid and not-found do not (`records::tests::only_an_unavailable_store_leaves_a_read_absent`), and a malformed S3 listing is still a dependency failure (`an_s3_read_failure_is_a_dependency_failure_not_a_forward`, `tests/domestic/source_s3.rs`). Red before the change: the zone and grid cases returned `Err(Provider)` (the gateway's 501), the grid case and the RSS and mid case asked no provider of the held families (`["Zones", "Warnings"]`).
- **NO-501, review RB-store-deadline / RB-listing-race / RB-zone-mid-starvation (Codex on #2916):** the observed grid, RSS and mid restores (listing and partition reads) end at the request bound and are raced from the head start, and a late zone read leaves the mids their providers' time. With twenty more current-observation partitions (over thirty, read eight at a time) each held to the catalog deadline, the answer comes within 3.5 s, equals the producing process's and asks the latest publication once (`many_grid_partitions_past_the_catalog_deadline_answer_from_the_provider`); with the current-grid, RSS and mid listings held, each latest publication is asked once between 650 ms and 1.5 s (at the head start) and the answer equals the producing process's (`late_listings_start_the_providers_at_the_head_start`); with only the forecast-zone list stored and its read held, the first answer's mid data equals a process whose zone read is prompt, each mid family asked once (`a_late_zone_read_leaves_the_mid_providers_their_time`) (`tests/domestic/full_response.rs`). Red before the change: the first two answered after 8.05 s, the third had no mid forecast, land or temperature (`land-unavailable`, `temperature-unavailable`).
- **NO-501, review round 2 (Codex on #2916: RB-store-deadline, RB-zone-mid-starvation, RB-zone-refill):** the observed restores the request stops waiting for at its bound are not cancelled; they run as owned work and a later request answers from them, and one answer uses one zone list. In one process whose current-observation pages take 2.6 s each, the second request (its provider calls blocked by the memo) answers equal to the producing process's without asking the provider (`a_late_stored_read_answers_the_next_request_from_its_owned_restore`); with a stored zone list that moves Seoul to `11B10102` arriving at 1.2 s, after the mids started at the head start with the release's zones, the answer has its temperatures (`one_zone_list_answers_both_the_mids_and_the_assembly`); with every zone-list read taking 2.6 s, the next request uses the list the first one's owned read installed and asks the temperatures of `11B10102` (`a_slow_zone_read_fills_the_zones_of_the_next_request`) (`tests/domestic/full_response.rs`). Red before the change: the second request's answer differed from the producing process's; the mixed zone lists failed the answer (`Err(Provider)`, the gateway's 501); the next request asked no `11B10102` temperature. `an_empty_store_answers_each_existence_question_once` still holds (the acquisition installs its list in the held zones without another read).
- **ALLOCATOR:** mimalloc is the global allocator of every binary, example and test of the crate: heap allocations, small, large and on another thread, lie in mimalloc's heap region (`allocator_tests::heap_allocations_come_from_mimalloc`, `src/lib.rs`). Red: with the `#[global_allocator]` line commented out the test fails. `Cargo.lock` stays consistent (`--locked` builds and tests). The musl release artifact is built and verified static by CI's Linux job; it is not built locally.
- **ACCEPT-CLOCK:** the observed request's waits count from the gateway's accept: with a geocoder that answers after 300 ms, station providers that never answer and an empty in-memory store, the gateway answers 200 exactly 2.5 s after the accept on a paused clock (`the_observed_wait_counts_from_the_accept_of_the_request`, `tests/domestic/full_response.rs`). Red before the change: 2.8 s.
- **MEASURE (coordinator, EC2):** seven or more restarts of the CI musl binary of this PR on the 2026-11-09 setup: no answer with 501; first-answer time per restart; client validation of each first answer against the same process's later answer and against production; CPU profile shows whether musl's lock contention is gone.
- **DOCUMENTS:** `docs/architecture/server2.md` (request bound, restart race, restart bound section) and `docs/architecture/server2-kma-data-design.md` (one wait for a request) describe the behaviour, the dependency and the accept clock.
- **PLACEMENT:** the placement gate passes against `server2/config/tasks/KMA-RESTART-BOUND.json` (base `origin/feat/2614-kma-restart-cpu`), and the artifact policy passes on outgoing commits.

Failure paths: a provider failure during a raced read leaves that part to the stored read or, when the read failed too, absent for this answer (never 503 or 501 for late or unavailable data); a read failure after the race keeps the provider data; a read with an unread partition records no S16 summary.
