# Alarm preparation retry specification
Input: [intent](../intent/issue-2677.md). Scope: `server/lib/pushCoordinator`.

**Weather source.** A new `weatherSource` module owns the weather HTTP call used by alarm and conditional preparation. It keeps the 60 s shared promise per URL and language, never caches a rejection, and admits at most `PUSH_WEATHER_CONCURRENCY` (default 16) simultaneous origin requests; the 5000 ms request timeout starts when a request is issued, not while it waits. Failures become a typed `PreparationError` (`stage: 'preparation'`) with a fixed message and a safe `code`: `weather-timeout` (request timeout/abort), `weather-unavailable` (network error, HTTP 408/429/5xx, empty body) are `retryable`; other HTTP 4xx is `weather-rejected`, not retryable. Messages and fields never contain URLs, coordinates or bodies.

**Dispatcher.** The dispatcher separates the preparation phase from the send phase. A retryable `PreparationError` thrown by `job.prepare` is retried with bounded exponential backoff and jitter (`prepareRetryMs` default 1000, doubling) up to `prepareAttempts` (default 4, `PUSH_PREPARE_ATTEMPTS`) total preparation calls, never past `job.deadline`: when the next delay would reach the deadline the item ends `expired` (stage `preparation`), when attempts are exhausted it ends `failed` (stage `preparation`, reason = error code). A retry re-enters the queue, so the existing start guard (registration revision, eligibility, disabled/generation state) runs again before preparing and after preparing, before any send; a changed registration ends `superseded`. Other preparation errors stay terminal (`failed`, reason `preparation-error`). Preparation attempts (`item.preparations`, may start from the job's persisted count) are separate from transport attempts (`item.attempt`, unchanged 5-attempt rule). Send-phase failures keep their rules: ambiguous timeout and any send error without a retryable status/code are never resent; they now end with stage `transport` and reason `transport-error` instead of the misleading `preparation`. Results carry `{status, error, stage, attempts, preparationAttempts}`; `reason` strings are allow-pattern sanitized (`^[A-Za-z0-9_.:/-]{1,64}$`, else `unknown`) and `error.message` is never copied.

**Engine.** On completion the job stores only `stage`, `reason`, `attempts` (transport) and `preparationAttempts` (cumulative across supersession and coordinator restart because parts persist them); a superseded job returns to `pending` and keeps the cumulative preparation count so repeated failures cannot retry indefinitely. The campaign manifest gains `summary`: job count by status, failure counts keyed `stage:reason`, and total preparation/transport attempts, rewritten with each checkpoint. `schemaVersion` stays 1; readers ignore unknown fields and old campaigns without them still load.

**Compatibility and rollback.** No storage layout or API change; revert the commit to roll back. Warning campaigns use sync preparation and are unaffected except for the stage/reason fields.

**Verification strategy.** Offline regressions in `server/test/offline` with fake request/FCM; no network, credentials or production access. The scheduled-batch test drives the real Engine, Dispatcher and weatherSource with a fake origin that times out once, then recovers.
