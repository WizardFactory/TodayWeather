Forecast narratives in weather responses

API contract · #2798 · verified locally 2026-10-17

Existing weather responses gain an optional forecastNarrative object. The warning screen and its types 1–4 stay unchanged. No new endpoint or client code is introduced. A later mobile app update must parse and display the field.

Actual isolated HTTP/Mongo response excerpts below use synthetic provider prose and unrelated weather collaborators. They are not live provider captures or deployed mobile screenshots.

4. Interpret time and text

17:00 KST is 08:00 UTC. announcement and expiresAt are true UTC ISO instants. Keep the original line breaks and Korean prose. textFormat: plain means literal, untrusted text: bind it as text, never HTML. Markup characters in these examples must remain inert. Prose and its embedded units are not translated or converted.

5. Optional availability

Missing, invalid, wrong-office, future or age ≥24h data omits only forecastNarrative. A two-second DB read deadline also preserves weather success; late reads cannot change the response. Requests never call the provider. Cache freshness is capped at 300 seconds and the publication’s remaining lifetime.

6. What was verified

The isolated smoke exercised 10 offices, all 17 provinces, real local HTTP and Mongo/Mongoose 5.13.23, shared v000901/v000902/v000903 responses, coordinate selection, national root selection, repeat/new concurrent publications, DB failure, expiry and unchanged warning types 1–4. It does not prove production Mongoose 5.1.2, live regional access, mobile display or deployed readback.

Deployment/restart and origin/public readback need separate operator approval. Restore saved overlays and affected workers for rollback; leave isolated narrative rows unused. Keep issue #2798 open until deployed acquisition/readback is verified. Mobile presentation/localization is #2803.
