# Rewrite verification matrix

Baseline: `bd6640f2` (re-baselined 2026-09-25 from `ff7acf3996ccb66c912d2ed4710cf300197d6966`, first written 2026-09-23; client and native source are identical at both commits); extended by the 2026-09-24 gap review and the 2026-09-25 final round (V37 added; V01, V03, V05, V10–V13, V15, V17, V24, V29, V30 and V33 extended). The re-baseline added V38–V42, extended V01, V02, V04, V05, V11, V15, V16, V25, V29 and V30, corrected the V26 anchor, and lists its re-runs under [re-baseline evidence](#re-baseline-evidence-bd6640f2-2026-09-25). These are proposed acceptance cases for a rewrite. Source inspection, the saved simulator screenshots and the probe records under [probes](../../reports/rewrite-verification/probes/) are existing evidence; the behavioral tests below have not been executed as part of this documentation task. Where an expected legacy value is labelled synthetic execution or probe, an isolated run in the gap review produced it; the six Node probe records (`client-*`, `server-*`) can be repeated from the repository with plain `node`, while the start-popup and photo-selection records need the [capture harness](../../reports/rewrite-verification/capture/README.md); every other legacy expectation is source-level and must be characterized before it is relied on. Use the [playbook](rewrite-playbook.md) for staging and the [decision register](decisions-and-open-questions.md) for intentional changes (A/D IDs below refer to it).

| Layer | Controlled inputs | Required evidence |
| --- | --- | --- |
| Contract/transform | Fixed request, raw product fixtures, clock/timezone, units/language | Exact legacy and replacement outputs; differences explained by field and stage |
| State/interaction | Stubbed HTTP, storage, native bridge and timers | Ordered events, selected city identity, persisted values, visible result and failure handling |
| Rendering | Known normalized data and documented viewport/native host | Screenshot plus route, product, fixture, revision, device/OS, safe-area mode and capture time |

| Release/runtime | Approved release configuration and scoped operational checks | Actual native/plugin and deployment results; never inferred from fixtures or source inspection |

## Acceptance record template

For each executed case, record: case ID; revision; fixture/hash; clock and timezone (process `TZ` as well as the fixture clock); product/platform; requested units/language; old/new status and output; observed difference; linked decision if intentional; screenshots/logs; result; remaining limitation. For runtime checks, add deployed revision and observation time.

A rewrite milestone passes only when its relevant cases have executed and unexplained differences have owners or are resolved. Source anomalies in the decision register remain unverified runtime scenarios until reproduced. Product and operations owners still need to define performance, freshness, accessibility and rollout thresholds; this document supplies no invented numerical targets.
