Existing defects should not become accidental requirements, and corrections should not be disguised as unchanged behavior.

## Evidence labels

- **Source observation:** directly traceable to checked-out code; it does not establish production frequency or user impact.
- **Isolated evidence:** a documented fixture/simulator reproduction with controlled dependencies (synthetic execution, probe or capture); it does not prove production parity.
- **Deployment observation:** a separately timestamped host/AWS fact; recheck before relying on it for rollout.
- **Proposal/open decision:** future behavior or evidence still requiring implementation, verification or product/operations choice.
- **Resolved upstream:** the described code no longer exists at `bd6640f2`; the row keeps the `ff7acf39` observation for history and names the commit and the current source line. A rewrite that ports older deployed code (the inspected service host runs `5bca407`, which predates both baselines) can still meet the old behavior.

## Recording a resolved decision

For each resolved item, add: owner/date, evidence/reproduction, chosen behavior, alternatives and reason, affected API/client/storage versions, migration/rollback plan, and verification IDs/results. Keep the source observation intact and mark it superseded only when the implementation baseline changes. When an upstream commit removes the behavior, as at the `bd6640f2` re-baseline, mark the affected part "resolved upstream in `<commit>`" with the current source line and keep the ID; a new anomaly gets the next free ID. Do not mark an item resolved merely because a new framework or provider was selected.
