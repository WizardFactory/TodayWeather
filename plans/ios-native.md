## IN-01 — project skeleton, imported assets and CI (#2950)

Design skipped: no system flow; the layout follows #2948 and the Android module split. Archify not applicable (the service overview gains the iOS client in IN-19, as the Android client does in AN-19).

## IN-02 — golden corpus and Swift weather core (#2951)

Design skipped: there is no new system flow. The port follows the Android core module by module, and the corpus decides behavior. Archify is not applicable (no route, collector or storage change).

- **Copy:** `ios/tools/import_corpus.py` copies the tracked files of `android/core-domain/src/test/resources/corpus/` byte for byte into `Core/Tests/TWDomainTests/Corpus/` (bundled with `.copy`) and writes `provenance/corpus.json`. CI's build job re-runs it, and both trigger lists include the Android corpus path. The standalone job reads only the copy.
- **Model:** `TWModel.JSONValue` keeps member order and number texts, so the comparison checks member order and integer versus fractional numbers, which the Kotlin tests do not. The views of `Models.kt` are protocols and structs over `JSONObject`.
- **Domain:** a Swift port of `Js.kt`, `Text.kt`, `WeatherConverter.kt`, `AirQuality.kt`, `Nationwide.kt`, `Warnings.kt` and `ChartPosition.kt`. The JVM APIs are replaced: `BigDecimal` rounding by the exact printf expansion with half-up rounding on its digits, and `Calendar` by proleptic Gregorian arithmetic with `TimeZone` offsets. The Swift port follows JavaScript in two places where the Kotlin emulation differs outside the corpus (exponential number text, boolean air grades); [`ios/tools/corpus/differences.md`](../ios/tools/corpus/differences.md) lists them.
- **JavaScriptCore:** `ios/tools/corpus/compare_jsc.py` runs the unchanged generator in the macOS `jsc` shell, with Node's `vm`, `fs`, `crypto` and `path` provided by `node-shim.js` and one run per time zone. It compares 2,611 cases. In `special.json`, 21 values differ: JavaScriptCore rejects day overflow and accepts second 60. `Warnings.jsDate` follows JavaScriptCore, and the tests expect the JavaScriptCore output for exactly those values (`JavaScriptCore/differences.json`). Under #2948 decision 2 this holds until IN-06 records the decision.

## IN-03 — Cordova data migration and simulator upgrade test (#2952)

Design note: the per-key rules port the Android `CordovaMigration` (AN-03) to Swift in `TWStorage`, which uses Foundation and SQLite only and runs under `swift test`. iOS differs in where the data lives. `localStorage` is read from WebKit's files, not through a `WKWebView` serving `app://localhost`: a web view needs the main thread and a web content process, which a background start may not get, and WebKit would open, and could migrate, the files it serves. The database and its write-ahead log are copied and the copy is read, so the source stays byte-identical. On the iOS 26.5 simulator the newest writes were only in the `-wal` file, and the layout was `Library/WebKit/<bundle id>/WebsiteData/Default/<hash>/<hash>/LocalStorage/localstorage.sqlite3`, located through WebKit's `origin` file. The device path without the bundle ID and the older single-directory file are supported from WebKit's source, not observed. The App Group suite is read through `UserDefaults`, typed as the plugin stores values. Stored texts are parsed by IN-02's strict `TWModel.JSONValue`, and stored strings and keys are compared by UTF-16 code units (`JSString`); the state file is written through `JSONValue`, so Cordova records keep member order, number texts and keys that differ only by normalization. Analytics: Firebase 13.1.1 `FirebaseAnalyticsCore` (the Cordova build's variant without ad-ID and on-device conversion), pinned by the committed `Package.resolved`. Collection is disabled and consent denied before `FirebaseApp.configure()`, which runs only with a `GoogleService-Info.plist` in the bundle; on the simulator the persisted flag changed from 1 (Cordova opt-in) to 2 before `configure`. The upgrade test needs the App Group entitlement, which simulator builds carry in the executable when signed for the simulator; CI builds keep `CODE_SIGNING_ALLOWED=NO` and do not run it. Archify not applicable (no service flow change; the app's start only).

## IN-04 — push re-registration after the update (#2953)

Design note (AK, 2026-11-15: acceptance and background completion as the Android app; [decision](../docs/evidence/tasks/ios-in-04-design-review/decision.md)): the requests port the Android `PushRegistration` (AN-04) to `TWStorage` (Foundation only, `swift test`), with `type: "ios"` (`Push.init` sets it on iOS whatever was stored) and `/v000903` paths. The oracle is the Cordova `Push` service run in the macOS JavaScriptCore shell, the engine of the Cordova iOS app, with the platform reporting iOS (`ios/tools/push/generate.py`); its cases are the Android corpus cases plus tokens delivered while the app runs, and they equal the Android corpus but for `type` and the device ID. `PushSync` (`TWData`) is the Android `PushSync`: one registration at a time, each reads the state, sends its requests one after the other and then stores the token, whether or not a request succeeded. A token FCM delivers while the app runs is first stored in `PushTokenQueue` (the Android app's WorkManager) and leaves it only after the state holds it, so the next process, opened or started in the background, completes a registration the previous one did not finish. The token is stored through IN-07's `AppStateHolder`, the single writer of the state. Not reproduced, as in the Android app: Cordova's 3-second timer before the list post and its requests that are not awaited.

History: PR #2975 first had this shape (`d3c156f3`). Review rounds 1–10 (CODEX-IN04-1..15, in the PR's comments) replaced it with a replay of the Cordova timeline and a durable replacement log, and the review reached its iteration limit. The design re-review of 2026-11-15 ([record](../docs/evidence/tasks/ios-in-04-design-review/README.md)) and AK's decisions returned to the Android shape. Kept from those rounds: the upgrade test through the app's start path (CODEX-IN04-2), continuations resumed exactly once in the test doubles (CODEX-IN04-3), no test hooks in app code (CODEX-IN04-7), and one rule for first and blank tokens (`isFirst`, `accepts`; CODEX-IN04-9, -10). Withdrawn: the Cordova timing (CODEX-IN04-1) and everything that served the log (CODEX-IN04-4..6, -8, -11..15). AK reset the review count on 2026-11-15 ("리뷰 횟수 0으로 바꾸고 구현 진행"); the new review runs under SDLC task `ios-in-04-android`.

## IN-17 — rollback hand-back to the Cordova app (#2966)

Design note: a port of the Android AN-17 with the iOS suite. The contract (marker `_twHandBack`, schema 1, generation, `complete`, the twelve owned keys and their Cordova texts) and the texts (`CordovaHandBack`), the re-migration after a fallback build's claim (`MigrationRunner`, `MigrationInfo.handBackGeneration`) and the consent rule (`HandBackConsent`) are Foundation-only `TWStorage` code; the reader is the existing `TwStorage.init`/`_handBack` in `client/`, unchanged (no iOS fix was needed: the plugin's iOS `fetch` returns a stored `NSString` as the same text, checked with `"` and `\` in a name). iOS differs in one place: `UserDefaults` has no multi-key commit, so `HandBackWriter` writes the next generation's marker incomplete first, then each owned key whose stored value differs, then the marker complete; the fallback build refuses an incomplete marker (keeps its own state, trusts no stored grant) and a native start does not take it for a claim, and the next process writes the whole hand-back again. The oracle for that order is the Cordova reader itself: `ios/tools/handback/generate.py` runs `TwStorage.init` with the plugin's JavaScript over a model of `AppPreferences.m` in the macOS JavaScriptCore shell for every prefix of the writes and of a write interrupted at each step and done again, and `HandBackWriterTests` hold the Swift writer to those operations. The writer runs after each saved state (`AppStateHolder`'s new `onSaved`, from the migration's state on, in save order) and after each write of the analytics choice (`HandBackConsentRecords`, wrapping IN-15's files); `AppStartup` checks a stored grant against the suite before the migration, so before the process hands its own choice back (on Android `EarlyStartProvider` runs before anything). Only a build with the App Group container writes. Archify not applicable (no route, collector or storage change on the server).

- **Shared files:** `AppState` (`MigrationInfo.handBackGeneration`, written only when set, so earlier state files keep their bytes), `AppStateStore` (`MigrationRunner.marker`), `AppStateHolder` (`onSaved`), `AppStartup` (the marker, the consent check), `AppLaunch` (`handBack`), `Monetization` and `AnalyticsConsentFiles` (the records and a choice read off the main actor), `CordovaUpgradeTests` and `check_upgrade.py` (the suite now holds the hand-back: compared with the migrated state instead of byte-identical), `build-cordova.sh` (commit and version), `recorder.py` (reports), the workflow (generator and path filters); for the scene sessions `TodayWeatherApp.swift` (removed: `AppScenes.swift` with `AppDelegate`, `SceneDelegate`, `WarmStarts`), `Support/Info.plist` (the scene manifest) and the project file (no generated scene manifest).
- **Not built (decided):** no test, mock or dry-run mode; tests inject the suite, the files and the SDK. No `client/` change (AK's standing rule for `client/www`); the empty-WebView limit below is reported instead.
